# Архитектура — Telegram Proxy Userbot

## Что это и зачем

Прозрачный прокси для Telegram-групп. Юзербот-аккаунт состоит одновременно в группах мерчанта и саппорта. Любое сообщение в одной группе автоматически пересылается в парную — так агенты поддержки никогда не появляются в пространстве мерчанта, а мерчант не знает, что говорит с командой через посредника.

---

## Структура модулей

```
cmd/userbot/        — точка входа: флаги, инициализация, graceful shutdown
internal/config/    — парсинг YAML + валидация при старте
internal/storage/   — интерфейс Storage и реализация на PostgreSQL (pgx/v5)
internal/bridge/    — диспетчер событий, ретрансляция, retry, humanizer
internal/scheduler/ — расписание смен, переключение аккаунтов
internal/tg/        — обёртка над gotd/td: соединение, диспетчер апдейтов, panic recovery
migrations/         — SQL-миграции (goose)
deploy/             — Dockerfile + docker-compose
```

### Связи между пакетами

```
main
 ├── config       (загрузка и валидация)
 ├── storage      (PostgreSQL пул)
 ├── scheduler    (Run — блокирующий цикл смен)
 │    └── tg      (Client.Connect / Disconnect)
 │         └── bridge  (SetBridge после Connect)
 └── bridge
      └── storage (FindBy* / SaveMapping)
```

`bridge` не зависит от `tg` и `scheduler` — только они зависят от него. Это позволяет тестировать bridge без Telegram-соединения.

---

## Поток данных (один цикл ретрансляции)

```
Telegram MTProto
    │  UpdateNewMessage
    ▼
tg/client.go  →  dispatcher.OnNewMessage()
    │  recoverBridge("OnNewMessage", ...)  ← panic recovery
    ▼
bridge/messages.go  OnNewMessage()
    │  1. IsRelevant? (chat в парах && не от self)
    │  2. Pair disabled? (CHAT_WRITE_FORBIDDEN ранее)
    │  3. resolveReplyTarget() — FindByTarget в PostgreSQL
    │  4. humanizer.Wait(ctx)  — случайная задержка 1–4 с
    │  5. withRetry(sendMessage) — 4 попытки, FLOOD_WAIT, CHAT_WRITE_FORBIDDEN
    │  6. SaveMapping() — INSERT в PostgreSQL
    ▼
Telegram MTProto  →  сообщение появляется в парном чате
```

## Принятые решения и trade-offs

### 1. MTProto (gotd/td) вместо Bot API

**Решение:** использовать MTProto-клиент `gotd/td`, а не Telegram Bot API.

**Почему:** Bot API работает только с bot-аккаунтами (токен `@BotFather`). Бот не может состоять в группе как обычный участник и не получает все апдейты от других участников. MTProto позволяет использовать полноценный userbot-аккаунт — он виден в группе как обычный человек и получает все события.

**Цена:** MTProto значительно сложнее Bot API. `gotd/td` — единственная активная MTProto-библиотека на Go; альтернатива `xelaj/mtproto` не развивается.

---

### 2. Session-файлы на диске + BoltDB вместо PostgreSQL для состояния gotd

**Решение:** сессии (`*.session`) и updates-state (BoltDB `*.bolt`) хранятся в Docker-томах на диске, а не в PostgreSQL.

**Почему:** gotd имеет встроенную поддержку `session.FileStorage` и `boltstor.NewStateStorage`. Нативная интеграция надёжнее, чем самостоятельная имплементация gotd-хранилища поверх pgx. Разделение инфраструктурного состояния gotd и бизнес-данных (`message_mappings`) упрощает бэкапы и отладку.

**Цена:** три вида хранилища вместо одного. При миграции сервера нужно переносить и файлы, и дамп БД.

---

### 3. In-memory кэш реакций без персистентности

**Решение:** текущее состояние реакций для каждого сообщения хранится только в памяти (`map[messageKey]reactionState` с RWMutex + TTL 24 ч).

**Почему:** Telegram присылает только агрегированный снимок реакций в каждом `UpdateMessageReactions`, без diff. Чтобы понять, что добавилось/убралось, нужно сравнить с предыдущим состоянием. Хранить это в PostgreSQL избыточно — данные эфемерны и нужны только на период жизни процесса.

**Цена:** после рестарта кэш пуст. Первое обновление реакций после рестарта может зеркалировать неполную дельту (добавит все текущие реакции вместо только новых). На практике это заметно только при активной работе в момент рестарта.

---

### 4. Без ORM — raw pgx

**Решение:** все SQL-запросы — константы в `storage/postgres.go`, выполняются через `pgxpool`.

**Почему:** одна таблица (`message_mappings`) с четырьмя запросами (INSERT, SELECT×3). ORM (gorm, sqlboiler) добавил бы зависимость и скрыл индексы от читателя кода. Raw `pgx/v5` + `pgx.RowToStructByName` дают типобезопасность без магии.

**Цена:** SQL-запросы не проверяются компилятором. Синтаксические ошибки проявятся только в тестах.

---

### 5. Scheduler как отдельный пакет с интерфейсом AccountController

**Решение:** `scheduler.AccountController` — минимальный интерфейс (`Connect`, `Disconnect`, `Phone`). `ClientController` в `orchestrator.go` его реализует, оборачивая `tg.Client`.

**Почему:** позволяет тестировать логику смен (`activeShift`, переключение) без реального Telegram-соединения — достаточно `mockController` с атомарными счётчиками. В тестах Scheduler вызывает те же методы, что и в проде.

**Цена:** дополнительный слой абстракции. Если понадобится расширить логику подключения — нужно менять два места (`ClientController` и тесты).

---

### 6. Per-account BoltDB (отдельный файл на аккаунт)

**Решение:** каждый аккаунт получает собственный BoltDB-файл вида `state_79001234567.bolt`.

**Почему:** BoltDB открывается с эксклюзивной блокировкой файла. Два аккаунта не могут делить один файл. При пересменке новый аккаунт открывает свой файл и продолжает catch_up с той точки, где остановился в прошлый раз.

**Цена:** несколько файлов состояния в томе `userbot_state`. Оператор должен следить, чтобы каждый файл был в персистентном томе.

---

### 7. Album-буферизация через таймер в tg/client.go

**Решение:** альбомные сообщения (одинаковый `GroupedID`) накапливаются в `albumBuffer` с 500 мс таймером. По истечению таймера (или при 10 элементах) вызывается `bridge.OnAlbum`.

**Почему:** gotd не буферизует альбомы на уровне `events.Album` в режиме raw-диспетчера с `updates.Manager`. Telegram гарантирует доставку всех элементов альбома подряд, но не атомарно — нужен небольшой таймер.

**Цена:** задержка 500 мс перед обработкой любого альбома. При очень медленном соединении (> 500 мс между элементами) альбом может быть частично разбит.

## Что намеренно не вошло в MVP

| Что | Почему оставлено за рамками |
|---|---|
| Метрики (Prometheus / OpenTelemetry) | Не требуется в ТЗ; структурированные JSON-логи покрывают наблюдаемость |
| Персистентный кэш реакций | Перезапуски редки, потеря дельты некритична |
| Redis / очереди сообщений | Одна пара сервисов, нет необходимости в асинхронной шине |
| Веб-интерфейс / API | Не требуется; управление через конфиг и `--check` |
| Поддержка групповых чатов (не супергрупп) | Telegram API отличается; в ТЗ подразумеваются каналы/супергруппы |
| Автоматическое восстановление при AUTH_KEY_UNREGISTERED | Сессия повреждена — оператор должен заново запустить `--auth`; автолечение рискованно |
| Ротация логов | Ответственность Docker / journald; не нужна в коде |
